# System Inventory — architecture

A module that records every piece of office computer hardware Synovative
owns: what it is, its details, a unique ID for each piece, which workstation
it sits in, and who that workstation belongs to.

**Status:** built (phase 1). Migrations `0010_inventory_notification.sql` and
`0011_system_inventory.sql`; page `/inventory`; "My system" on the Profile.
Section 9 lists what is left for later. An expanded draft of this design
(models catalogue, locations, laptops, acknowledgements, audits) is in git
history; this simpler one was chosen.

---

## 1. What it does

- Keeps a register of every hardware **component**: processor, motherboard,
  RAM, storage ("ROM"), GPU, power supply, cabinet, monitor, keyboard, mouse,
  UPS, accessories. Each one has its details and a **unique asset ID**.
- Records **where each component is**. Internal parts sit inside a
  **cabinet**. A cabinet, its monitors and its peripherals together make a
  **workstation**.
- **Allots each workstation to a user**, who is notified and sees it on their
  Profile.
- Shows what is **spare**, what is **under repair**, and what is **retired**,
  and keeps a full **history** of every change.
- Only **Super Admin** and **Admin** can add or change anything (section 6).

## 2. The three levels

```
Workstation  WS-012  "Design desk 4"          → allotted to: Neha Choudhari
├── Cabinet  SYN-CAB-0012  Cooler Master Q300L
│   ├── Motherboard  SYN-MBD-0012  ASUS B550M
│   ├── Processor    SYN-CPU-0012  Ryzen 5 5600
│   ├── RAM          SYN-RAM-0031  16 GB DDR4 3200
│   ├── RAM          SYN-RAM-0032  16 GB DDR4 3200
│   ├── Storage      SYN-STO-0019  512 GB NVMe SSD
│   ├── GPU          SYN-GPU-0007  RTX 3060 12 GB
│   └── PSU          SYN-PSU-0012  650 W
├── Monitor  SYN-MON-0021  Dell P2422H 24"
├── Keyboard SYN-KBD-0012
├── Mouse    SYN-MOU-0012
└── UPS      SYN-UPS-0004
```

| Level | What it is | Rules |
| --- | --- | --- |
| **Workstation** (the "container") | One desk setup | Allotted to at most one active user at a time, or free. |
| **Cabinet** | A component of category Cabinet | At one workstation at most. Holds the internal parts. |
| **Component** | Any other piece of hardware | *Internal* parts go inside a cabinet; *external* ones go at a workstation; "Other" goes either way. Or nowhere: spare, under repair or retired. |

A component is in **one place at most**: inside one cabinet, or at one
workstation. Moving a cabinet moves everything inside it, because the parts
point at the cabinet, not at the desk.

## 3. Categories and their details

Every component has: asset ID, category, brand, model, serial number,
status, purchase date, price, vendor (from the Vendors module), warranty end
and notes. On top of those, each category asks its own details:

| Category | Prefix | Goes in | Details |
| --- | --- | --- | --- |
| Processor | `CPU` | Cabinet | Cores, threads, base clock, socket |
| Motherboard | `MBD` | Cabinet | Chipset, socket, form factor, RAM slots, max RAM |
| RAM | `RAM` | Cabinet | Capacity (GB), type (DDR3/4/5), speed (MHz) |
| Storage (SSD / HDD, "ROM") | `STO` | Cabinet | Type (NVMe / SATA SSD / HDD), capacity |
| GPU | `GPU` | Cabinet | Chipset, VRAM |
| Power supply | `PSU` | Cabinet | Wattage, 80+ rating |
| Cabinet | `CAB` | Workstation | Form factor, colour |
| Monitor | `MON` | Workstation | Size, resolution, panel, refresh rate |
| Keyboard | `KBD` | Workstation | Wired / wireless |
| Mouse | `MOU` | Workstation | Wired / wireless |
| UPS | `UPS` | Workstation | VA rating |
| Accessory | `ACC` | Workstation | Headphones / webcam / speaker / dock |
| Other | `OTH` | Either | What it is |

- The details live in one `specs` JSON column. Their fields per category are
  `INVENTORY_CATEGORIES` in `lib/types.ts`; adding a field needs no migration.
- Prefix and "goes in" are also in the database
  (`inventory_category_prefix()`, `inventory_category_place()` in `0011`). **A
  new category goes in both places**, with a new migration.

### The unique asset ID

- **Format:** `SYN-<PREFIX>-<4 digits>`, e.g. `SYN-RAM-0031`. Workstations:
  `WS-001`.
- **Generated by the database** on save, from one counter per prefix taken
  under a row lock, so two people adding at once never clash. An ID the app
  sends is ignored.
- **Never changes and is never reused**, even after a delete. After 9999 it
  grows to five digits rather than being cut off.
- **The category is fixed** once saved, so the prefix can't lie. A wrong
  category is fixed by deleting the entry and adding it again.
- **The manufacturer's serial** is stored too and must be unique when filled
  in (ignoring case and spaces), which catches double entries. Blank is fine.

## 4. Database (`0011_system_inventory.sql`)

| Table | Holds |
| --- | --- |
| `workstations` | `code` (generated), name, location, `assigned_to` → profiles, `assigned_at`, notes |
| `inventory_items` | Every component, cabinets included: `asset_tag`, category, brand, model, serial, `specs`, status, `cabinet_id` → inventory_items, `workstation_id` → workstations, purchase date, price, `vendor_id` → vendors, warranty, notes |
| `inventory_events` | History: who, when, what (`kind`), the asset ID or code, from → to, note. Written only by triggers |
| `inventory_counters` | The last number used per prefix. Not readable from the app |

### Rules the database enforces

| Rule | How |
| --- | --- |
| In one place at most | Check: `cabinet_id` and `workstation_id` never both set |
| Internal parts only inside a cabinet; cabinets and external items only at a workstation; parts only inside a *cabinet* | `inventory_guard_item` trigger |
| Status follows placement: placed is In use, taken out is Spare (or Under repair / Retired if chosen) | Same trigger |
| Under-repair and retired items can't be placed; nothing goes into a retired cabinet; a cabinet holding parts can't be retired | Same trigger |
| IDs generated, never reused, never cut off; ID and category locked | Same trigger + `inventory_counters` |
| Serial unique when filled | Unique index on `lower(btrim(serial_number))` |
| A workstation goes only to an active member | `inventory_guard_workstation` trigger |
| Deleting a cabinet or workstation never deletes its contents; they become spare | Foreign keys `on delete set null`, then the guard sets the status |
| Every change is logged, with who and an optional note; edits list the fields changed | `inventory_log_item`, `inventory_log_workstation` triggers |

### Functions the app calls

Moves go through these, so the app never sets two placement columns itself and
each move can carry a note into the history. Each checks
`can_manage_inventory()`.

- `inventory_install(item, cabinet, note)`
- `inventory_place(item, workstation, note)`
- `inventory_remove(item, status, note)`: takes it out (if anywhere) and sets
  Spare, Under repair or Retired. Also how a spare changes status.
- `inventory_assign_workstation(workstation, person or null, note)`

Adding, editing and deleting components and workstations are plain table
writes, limited by Row Level Security.

## 5. App

| Piece | Where |
| --- | --- |
| Page | `app/(app)/inventory/page.tsx`: tabs **Workstations**, **Components**, **Spares**; stats on top |
| Drawers and forms | `components/inventory/`: workstation drawer (allot, cabinet with its parts, items on the desk, history), component drawer (details, where, move / take out / under repair / retire, history), add/edit forms, pickers |
| Profile | `components/inventory/my-system.tsx`: "My system" — the desk allotted to you and what is in it, read-only |
| Sidebar | **Admin** section, "System Inventory", for those who can view it |
| Types | `Workstation`, `InventoryItem`, `InventoryEvent`, `INVENTORY_CATEGORIES` in `lib/types.ts` |
| Data | Scope `inventory` in `lib/data/db.ts`; history is read when a drawer opens (`loadInventoryEvents`) |
| Writes | Inventory actions in `lib/store.tsx`, all through `commit()` |

**Add component** asks the category first, then shows that category's
details. **Add another like this** keeps everything but the serial number, so
ten identical RAM sticks are quick to enter. A new component can go straight
into a cabinet or at a workstation, or into stock.

## 6. Permissions

| Who | Can |
| --- | --- |
| **Super Admin, Admin** | Everything: add, edit, move, allot, retire, delete |
| **Manager** | See the whole register and its history; change nothing |
| **Anyone with a workstation** | See their own workstation and what is in it, on their Profile |
| **Everyone else** | Nothing; the module is hidden |

As everywhere, the rules live in both places: `canManageInventory` /
`canViewInventory` in `lib/permissions.ts` for what the screen shows, and
`can_manage_inventory()` / `can_view_inventory()` with Row Level Security in
`0011` for what is actually allowed.

---

## 7. Notifications

Allotting a workstation tells the person ("Workstation allotted to you");
taking it back or giving it to someone else tells the previous holder. Type
`inventory_assigned`, added in `0010` (its own file, run before `0011`).

## 8. Decisions taken

| Question | Decision |
| --- | --- |
| What is "ROM"? | Storage (SSD / HDD). The category is Storage, labelled with "ROM" in the form |
| Can users see their own workstation? | Yes, read-only, on their Profile |
| Can Managers view the inventory? | Yes, read-only |
| Category list | As in section 3; more need a small migration |
| Existing Excel list to import? | None yet; add by hand |
| Laptops | Not tracked yet (section 9) |
| ID format | `SYN-RAM-0031` / `WS-001` |
| Price | Recorded on each component; visible to anyone who can see the component |

## 9. Later

- **Warranty reminders**: a daily notice to Admins for warranties ending in
  30 days (the Components tab already filters them).
- **QR labels** that open a component's page when scanned.
- **Laptops**, issued to a person rather than placed at a desk.
- **Import** from a spreadsheet.
- **Hiding prices** from people who only see their own desk.

## 10. Out of scope

- Software licences.
- Automatic hardware detection from the PCs.
- Repair tickets or vendor workflows. "Under repair" is a status only.
